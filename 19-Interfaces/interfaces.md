
## 前述
- 结构体更像是在描述“**它是什么**”
- 接口更像是在描述“**它能做什么**”
接口关注的不是内部字段，而是 方法集合。

接口通常有三个重要作用：
- 抽象行为：只关心“会不会做”，不关心“怎么做”
- 解耦：调用方依赖接口，而不是依赖具体实现
- 多态：不同类型，只要实现了同一接口，就可以被统一处理

> Go 判断一个类型是不是某个接口，不看继承层级，而是看：你有没有这些方法。
> 如果有一个接口 Reader 只要求 Read() 方法，而某个类型只实现了 Read()，那它就能赋值给 Reader 类型的变量



## 接口的实现
“谁实现了接口”这个判断，和值接收者 / 指针接收者有关。

给结构体定义方法时，方法接收者写成 `T` 和写成 `*T`，会不会影响这个类型是否实现某个接口？
- T 作为接收者时，方法拿到的是一个副本语义的接收者
- Go 在判断接口实现时，会涉及到 方法集（method set），而 `T` 和 `*T` 的方法集并不完全一样。

如果某个方法是这样定义的：`func (p *Person) Read() {}`，那么你觉得是 `Person` 能赋值给 Reader，还是只有 `*Person` 能赋值给 Reader？为什么？
- `Person` 像“这个人本体的复印件”, `*Person` 像“能直接找到这个人本人”
- 如果某个能力是定义在 `*Person` 上，就相当于这个能力要求“必须能找到本人，才能操作”。

> 接口实现看的是方法集
> T 和 *T 的方法集不同
> 定义在 *T 上的方法，不会自动进入 T 的方法集
> 所以“值类型是否实现接口”会受到接收者写法影响

```go
type Reader interface {
	Read()
}

type Person struct{}

func (p *Person) Read() {}

func main() {
	var r Reader
	p1 := Person{}
	p2 := &Person{}

	// A
	r = p1

	// B
	r = p2
}
```
在接口赋值时，编译器检查的是 p1 这个静态类型 Person 的方法集，而 Person 的方法集里没有 Read() 方法，所以 A 会报错。


那为什么 `p1.Read()` 不报错?
- 如果 Read() 是定义在 *Person 上，而 p1 又是一个可取地址的变量，编译器会帮你做一层隐式转换，等价理解成：`(&p1).Read()`
- `r = p1` 是接口赋值+接口实现检查。
> 方法调用：编译器有时会帮你“补地址”
> 接口赋值：编译器只按类型的方法集严格检查，不帮你改类型
```go
p1 := Person{}
p1.Read()   // 可能可以，理解成 (&p1).Read()
var r Reader
r = p1      // 不行，因为 Person 没实现 Reader
r = &p1     // 可以，因为 *Person 实现了 Reader
```


# nil

接口变量是不是 nil，不能只看“里面那个具体值是不是 nil”，还要看接口内部是否“真的什么都没有”。

一个接口值，内部可以理解成两部分：
- 动态类型
- 动态值
只有当这两部分都没有时，接口变量才真正等于 nil

```go
var p *Person = nil
var r Reader = p
```
- p == nil 是 true
- 但 r == nil 是 false
因为 r 里相当于保存了：类型：*Person，值：nil


在 Go 的常见风格里，接口往往更适合定义在“使用行为的一方”，也就是调用方 / 消费方。因为接口描述的不是“**我能提供多少能力**”，而是：**你到底只需要我提供哪些能力。**
比如有个函数只是想“读取数据”，那它更自然的想法应该是：“我只需要一个能 Read 的东西”而不是：“你必须实现我这个包里预先定义好的一整套接口”

> 所以 Go 里常见的思路是：实现方提供具体类型，使用方定义自己需要的最小接口
